# Components
- Smart Add is an in-place sheet: it previews the real files (SourcePreview, quiet viewer) and mounts NewExpense/StatementDeskPage with the embedded prop, which switches them to panel mode (no page header, ticket, toolbar, file pickers or drop zone; same state, checks and save path); hiding keeps in-flight work, there is never a second parser or posting path, and openSmartAdd('document') (src/lib/smart-add-event.ts) reads PDFs as documents without asking.
- More is a searchable category directory (ModuleDirectory): categories collapsed on open, one close control, recent pages in local storage only. Review reminders are grouped and de-duplicated for display by review-reminders.ts; Set aside items are restored only by removing their key from inboxDismissed.
- JournalToday (companion Today), CompanionReview and /spaces are presentation-only over existing store/review data; Spaces only sets homeScope and links, Review actions stay in the existing review flows, and the original overview tools keep their preference ordering inside the disclosure. Companion surfaces use the cmp-* classes and --companion-* tokens in styles.css; Smart Add is opened from anywhere via the ledgerline:smart-add window event so pages never navigate to add.
- Long settings-style pages use the shared Fold (details) component, which opens itself for a matching URL hash; pop-ups use the shared centred Dialog so phone sizing stays consistent.
- Smart Add post-save asset follow-up is register-only with the existing transaction/payment IDs; claim follow-up mounts the existing claim builder with that entry ID. Receipt originals already appear in DocuRepo through vaultItems, so follow-ups never upload a second original or post a second expense.

# Receipt-reading rules (src/lib modules these components use)
- Receipt reading uses the AI Gateway SDK in receipt-extract.functions.ts with the shared receipt-reading.ts schema; every printed non-tax line between subtotal and total (service charge, packing, delivery, fees, negative discounts) is its own charge, tax keeps its printed parts, items are always read with their section heading (never money), and the total check is subtotal + charges + tax + tip + round-off; subtotal/tax/tip arithmetic is checked at review and server save, items are opt-in line totals, field certainty stays separate and scanned categories require owner confirmation, so extraction never silently changes spending. Rounding to a whole unit (INR/JPY/KRW/IDR, gap under one unit) is accepted as implied round-off and saved as roundOff; printed round-off lines are read separately; decimal currencies stay exact. Low-confidence item fields must be acknowledged in review before confirming (acknowledgement is bound to the exact values, so any edit asks again), while item-vs-subtotal differences stay a review prompt that never blocks saving or later editing.
- Offline receipt photos (src/lib/offline-scan.ts) can be dropped from this phone one by one or all failed at once; only photos still waiting to be read are removable, a photo already read stays in Drafts, and every attempt writes back only while the photo is still pending so a late-finishing read can't resurrect one the owner removed.
- Receipt corrections: correctedFields compares the edited bill check against the saved reading (both kept in the draft), and a corrected field counts as owner-checked; only shop-name corrections are learned (shopAliases misread→corrected key via learnedShopName), never amounts or dates.

# Review, claim, trip and report rules (src/lib modules these components use)
- review-centre.ts derives overlapping issue counts, stable-ID selection and explicit category exclusions without altering money; unfinished review context uses owner-encrypted device storage and never restores an approved preview or triggers a save.
- review-workflow.ts derives scoped selection, action eligibility and badges using existing validators; Inbox navigation and ReviewHistory reuse the shared ledger and existing correction APIs, never a second review ledger. Transfer approval uses matching client and owner-scoped RPC validation, snapshot-checked retries/Undo and money-account restrictions; different dates/converted values or linked workflows stay blocked until independently preserved.
- review-mapping.ts previews reuse trip/activity atomic RPCs; review-metadata.ts uses revision/config-checked owner-atomic metadata RPCs with financial_corrections audit, idempotent requests and all-or-nothing undo. Payment mapping never moves source accounts; claims/splits are excluded. review-recurring.ts seeds planned commitments with stable insert ID/read-back, never expense creation; review-recovery.ts uses saved active instrument/unique configured tags only.
- Claim discovery is pure in claim-discovery.ts; preparation saves use owner-scoped revision and mutation IDs, with encrypted owner device recovery in claim-preparations.ts. The preparation hook serializes device writes, retains newer in-flight edits and retries recovered unsynced copies; stale revisions never overwrite another device. Linking reuses audited metadata transactions and never grants reimbursement eligibility.
- financial-review-intelligence.ts adapts saved narration to existing confirmed rule conditions without altering records; category-only ready suggestions require unchanged responsibility, and recurring cohorts partition ownership/type/claim treatment before reusing cadence detection.
- Travel calendar/reminder rules live in travel-calendar.ts and budget comparisons in trip-planning.ts; both derive owner-visible records without creating transactions.
- Trip metadata batches use manage_trip_expenses with owner and reviewed-snapshot checks, never monetary writes; trip-suggestions.ts (smartTripSuggestions) is pure and requires explicit linking. Travel inbox derives confirmations from vault attachments and stores manually added messages in owner preferences; it has no external email connection.
- Trip discovery filters are pure in trip-filters.ts: selections combine within a field and intersect across fields, date ranges overlap inclusively, and filtering never changes trips or ledger data.
- Trip budgets follow trip-budget.ts: one primary budget per trip; workspace/traveller/category/currency/organisation allocations are independent views that reconcile against it and are never summed together; actuals come only from the shared ledger via tripFinance, unpaid bookings stay commitments, and a budget-less trip with saved allocations shows "requires confirmation" rather than an auto-derived total.
- Trip advances apply to claims only as a user-entered amount per claim (applyAdvance in expense-claim.ts), capped by advance not applied in earlier saved claims; never automatic.
- trip-lifecycle.ts: cancel/restore only set cancelledAt/restoredAt; delete unlinks entries and is blocked while advances or claims are open. card-balance.ts derives running card owed from accountBalance; payments are reconciled only when reconciledAt is set.
- Reports Centre PDFs are built from src/lib/report-centre.ts (pure, reuses ledger/workspace/travel rules) and rendered by src/lib/report-pdf.ts; generated PDFs are frozen snapshots in report_history + owner receipts prefix so later edits never change them.
- Detailed Expenditure Statements are pure (src/lib/expenditure-statement.ts) and merged with original bills by pdf-lib in src/lib/expenditure-pdf.ts; payer, payment source and eligibility come only from saved entry, instrument and reimbursement records.
- Setup completion closes only after preference save succeeds; failure stays open for retry so the completion prompt is not falsely suppressed.
- Trip Budget Breakdown stages all dimensions locally and saves once; Cancel discards the whole draft and failed saves retain it for retry.
- PDF table cells with non-Latin text are rendered by the browser onto canvas images (src/lib/pdf-unicode.ts withUnicode) because jsPDF core fonts are Latin-only and cannot shape Indic scripts; titles, footers and bill-page labels use textU()/drawTextU() which image-render non-Latin text.

- ModuleDirectory groups all existing module destinations; the adaptive shell uses a short primary rail and native phone sheets, never a replacement ledger.
- Shared UIX controls use system typography, semantic theme roles and minimum touch sizing; Canvas disclosures retain mounted review fields and existing validation.
