# Statement and import rules
- financial-corrections.ts previews reuse ledger rules; atomic RPCs preserve source money and audit stale-safe undo. statement-evidence.ts extracts only labelled headers; identity/coverage require separate owner confirmations. statement-checkpoint.functions.ts derives saved immutable results from owner reads with atomic snapshot guards; account-statement-status.ts invalidates changed evidence and never uses upload dates for freshness.
- Excel statements use a dynamically loaded BIFF-capable SheetJS reader and real workbook fixtures so legacy XLS and XLSX share review rules.
- Statement transfer matching requires a selected account and its debit/credit side; competing near-equal matches remain manual to prevent arbitrary reconciliation.
- src/lib/statement-pipeline/ holds the one canonical statement model — line.ts (line shape, totals, balance projection), identify.ts (whose account, ask when unsure), match.ts (confidence-scored one-to-one matching), classify.ts, plan.ts (self-check and balance gates), apply.ts (posting and undo); new statement screens consume it instead of adding bank-specific parsers or matchers, so confidence reasons and posting gates stay identical everywhere.
- Card-credit classification in statement-auto.ts preserves refunds and otherwise uses card_payment; existingCardPayment reuses only unique exact original-money/date/account movements with narration/reference evidence. Historical postingBlockers also runs server-side, rejects card-credit income and non-card destinations; unknown source accounts require review.
- Historical statements use owner-scoped import_batches/import_rows staging and explicit import_rules; posting uses server-derived FX and atomic import_posts fingerprints, never changes existing ledger entries, and keeps original statement provenance.
- Rule matching in historical-import.ts uses literal source-description conditions, original currency/amount and highest priority; equal-priority conflicts stay unresolved and mappings are whitelisted so rules never grant approval or change source identity.
- Import manifests and overlap/outcome counts are pure in import-manifest.ts; each file has reviewed account/currency/period, detected transaction ranges never certify coverage, and post-interruption outcomes read persisted fingerprints rather than trusting response counts.
- Import inbox grouping/search validation lives in import-inbox.ts; batch links open owner-visible staged review only, never posting, and active reviews refresh with stale-response protection.
- Import approval previews and authenticated posting share source amount/date/currency and statement-account direction guards in historical-import.ts, matching the atomic posting checks so invalid movements never appear eligible.
- Statement review grouping lives in import-groups.ts as a pure presentation function; group totals use original amounts with incoming/outgoing kept separate, and grouping never changes classifications or approval.
- Import recurring-pattern hints reuse planning.ts cadence detection via import-patterns.ts, partition by account/currency/type/direction and retain every source row; hints never create commitments or treat repeats as duplicates.
- Classification learning uses import-learning.ts for conservative merchant/account/currency/type/direction matches; reusable mappings omit source identity and approval, and propagation leaves matching unconfirmed rows under review.
- Scanned imports extract four PDF pages per leased run with durable per-page results and owner AI pause guards; source balance quotes stay separate from user balance review, and matching arithmetic never certifies ledger completeness.
- Internal transfers: transfer_links (owner-read RLS, unique active debit/credit) written only by confirm_transfer/cancel_transfer RPCs; the debit becomes the single transfer movement and the credit keeps statement evidence via expenses.transfer_counterpart_of, which ledger/cashflow and store.transactions exclude so it is never counted twice. transfer-match.ts suggests pairs; "strong" needs a shared reference or narration naming the other account, never amount alone, and every link still requires confirmation.
- transfer-audit.ts is a read-only records check from April 2026 against uploaded statement lines pooled per account; coverage uses the dates the lines actually span, and findings never write records.
- statement-crosscheck.ts parses balance-column PDF statements on-device (direction from running balance) and only reports matches; the cross-check page never uploads, stores or posts statements.
- Forex card statements (forex-statement.ts) reconcile per currency wallet in the wallet's own currency; pass-through pairs (pass-through.ts) become transfers only via an explicit, undoable correction through a chosen holding account.
- Statement Desk upload history lives in owner preferences (statementUploads, max 10) so undo works from any device; scanned/photo statements are read by the existing server extractor and never auto-post (no printed balances). Coverage is derived from reconciled/statement-ref entries in statement-pipeline/coverage.ts.
- New entry suggestions (single-entry.ts) reuse these rules as tap-to-apply hints only; strong matches block Save until confirmed separate, so typed and statement entries share one rule set.
- Loan EMI matching (src/lib/emi-match.ts) feeds statement classification as an ask-first loan_repayment suggestion: same pay-from account or a narration naming the loan/linked-account refs (loan account details.matchRefs), due-date window −7/+5 days, gap ≤ max(₹100, 0.5%) or 10% when refs match; the loan-card reconciliation view is read-only.
- Unknown statement accounts: identify.ts reads labelled header facts (bank, number, IFSC, holder, type) into AccountHint; NewStatementAccount shows them editable and creates only on tap (duplicateAccount blocks copies), with newAccountFromHint using the printed opening balance or 0 and storing matchRefs. After posting, Statement Desk offers transfer_links for posted entries; only "strong" pairs are bulk-linkable, via confirm_transfer.
- Receipt drafts pair with statement debits in draft-match.ts (one-to-one; "sure" needs exact amount, ≤2 days, shop in narration and no rival; else "check", unticked). The bank line keeps amount/date; a paired draft adds files/shop/category and is marked saved with its files kept so Undo reopens it. summary.ts gives the pre-save reconciliation counts and balance gaps, report-only.
- Investment documents (src/lib/investments/demat.ts) are detected on Statement Desk before bank parsing and never enter the ledger; holdings are one row per owner/demat/ISIN, trades and gains attach only to existing ISINs (unknown ones are reported), lots/gains are fingerprinted so re-uploads add nothing, and valuation stays "price data required" until an authorised price source exists.
- Reconciliation success is measured by one project.statement_saved event per saved account, using summary.ts savedBalanceCheck on exactly the posted lines (declined asks count), never the pre-save projection; CSV/Excel exports carry no printed closing, so they report not_compared.
