# Finance rule modules
- payees.ts stores external directory records in owner preferences; explicit selection fills the existing merchant draft only, never an owned account or automatic financial classification. Directory changes do not relabel old ledger records.
- correction-fields.ts derives draft account fields from ledger movement/target rules; it never changes financial treatment or substitutes external payees for owned accounts.
- financial-corrections.ts previews reuse ledger rules; atomic RPCs preserve source money and audit stale-safe undo. statement-evidence.ts extracts only labelled headers; identity/coverage require separate owner confirmations. statement-checkpoint.functions.ts derives saved immutable results from owner reads with atomic snapshot guards; account-statement-status.ts invalidates changed evidence and never uses upload dates for freshness.
- review-centre.ts derives overlapping issue counts, stable-ID selection and explicit category exclusions without altering money; unfinished review context uses owner-encrypted device storage and never restores an approved preview or triggers a save.
- review-workflow.ts derives scoped selection, action eligibility and badges using existing validators; Inbox navigation and ReviewHistory reuse the shared ledger and existing correction APIs, never a second review ledger. Transfer pairs with differing dates/converted values or linked credit workflows are blocked until the canonical movement preserves both independently; client guards are not a replacement for server validation.
- review-mapping.ts previews reuse trip/activity atomic RPCs; review-metadata.ts uses revision/config-checked owner-atomic metadata RPCs with financial_corrections audit, idempotent requests and all-or-nothing undo. Payment mapping never moves source accounts; claims/splits are excluded. review-recurring.ts seeds planned commitments with stable insert ID/read-back, never expense creation; review-recovery.ts uses saved active instrument/unique configured tags only.
- Claim discovery is pure in claim-discovery.ts; preparation saves use owner-scoped revision and mutation IDs, with encrypted owner device recovery in claim-preparations.ts. The preparation hook serializes device writes, retains newer in-flight edits and retries recovered unsynced copies; stale revisions never overwrite another device. Linking reuses audited metadata transactions and never grants reimbursement eligibility.
- V5.4 financial audit fixtures run only in memory; defect regressions assert real passing outcomes, and unresolved expected failures must never be counted as successful acceptance.
- Position reimbursement totals use outstandingOf on tracked expense claims; legacy workspace reports use workspaceParts, and manual loan splits use stored-INR repaymentParts while preserving principal-only legacy/EMI entries.
- Family permission SQL has an isolated PGlite regression covering active, unrelated and revoked requesters plus owner decisions; cloud tests must never create sample records in production.

- Personal/family tracker, no approvals: expense rules live as pure tested functions in src/lib/expenses.ts.
- Accounts/ledger rules (balances, cashflow, net worth) are pure tested functions in src/lib/ledger.ts; balances are derived from entries, never stored, and transfers/card payments never count as income or spending. store.expenses = expense-type only; store.transactions = all entries.
- Planning math (recurring schedule, forecast, safe-to-spend, loans, goals, subscription detection) lives in src/lib/planning.ts; src/lib/position.ts combines records into screen/AI figures. The AI assistant (src/lib/assistant.functions.ts) only explains facts from position.ts — never let it compute numbers.
- Mutual fund portfolio charts use pure tested rules in src/lib/portfolio.ts on owner-visible NAV snapshots; gain is change since the first saved NAV net of ledger flows, not lifetime return, because acquisition cost is not recorded.
- Long-range predictions are pure tested rules in src/lib/projection.ts (editable category inflation assumptions); suggestions are rule-based from those figures, not AI, so numbers stay verifiable.
- Financial inbox, data freshness and balance-discrepancy checks are pure derived rules in src/lib/inbox.ts; items are never stored, only dismissals, so they clear automatically when records are fixed and discrepancies never auto-create entries.
- Reimbursement claim detail lives in expenses.reimbursement (src/lib/reimbursements.ts); money back is a linked reimbursement-type entry, never income, and reimbursement_status is derived from it.
- Health score (src/lib/health.ts) and monthly review figures (src/lib/monthly-review.ts) are computed by tested rules; the AI only narrates saved reviews, which store a data hash to flag outdated reports.
- Phase 2/3 rules (simulator, behaviour, emergency fund, irregular bills, milestones, trips, merchants, weekly brief) are pure tested functions in src/lib/intelligence.ts; their settings live in finance_preferences, trips link entries by a 'Trip: <name>' tag so stored INR and exchange rates are never rewritten, and simulations never write records unless the user explicitly saves a planned commitment.
- Saved payment methods (UPI IDs, cards, wallets, cash) live in owner-scoped finance_preferences.paymentInstruments with pure tested rules in src/lib/payment-instruments.ts; each is linked to an account of a compatible kind and entries keep the method id plus the general payment type, so balances still flow through the linked account.
- Currency conversion happens server-side in src/lib/fx.functions.ts (Frankfurter/ECB rates for the bill date) so stored INR amounts can't be faked by the client.
- Reports are generated in the browser (src/lib/reports.ts) from data the user can already see, so RLS scoping applies automatically.
- Receipt reading runs in a server function (src/lib/receipt-extract.functions.ts) so the AI key stays server-side.
- Vault document scanning uses a server function (src/lib/document-extract.functions.ts) gated by the same AI privacy settings; extracted fields are always reviewed before saving.
- Category splits live in expenses.allocations and all category reporting goes through categoryTotals/categoryParts so a split transaction is counted once.
- Excel statements use a dynamically loaded BIFF-capable SheetJS reader and real workbook fixtures so legacy XLS and XLSX share review rules.
- Travel calendar/reminder rules live in travel-calendar.ts and budget comparisons in trip-planning.ts; both derive owner-visible records without creating transactions.
- Statement transfer matching requires a selected account and its debit/credit side; competing near-equal matches remain manual to prevent arbitrary reconciliation.
- Card-credit classification in statement-auto.ts preserves refunds and otherwise uses card_payment; existingCardPayment reuses only unique exact original-money/date/account movements with narration/reference evidence. Historical postingBlockers also runs server-side, rejects card-credit income and non-card destinations; unknown source accounts require review.
- Mutual fund NAVs are authenticated server-fetched daily quotes; reviewed units create dated valuation snapshots, never income or expense entries, so net worth reuses the ledger engine.
- Universal entry presentation rules (recent-first ordering, which detail groups show, date shortcuts) are pure functions in src/lib/entry-form.ts; they never decide amounts or what is saved, so the one save path stays unchanged.
- Historical statements use owner-scoped import_batches/import_rows staging and explicit import_rules; posting uses server-derived FX and atomic import_posts fingerprints, never changes existing ledger entries, and keeps original statement provenance.
- Rule matching in historical-import.ts uses literal source-description conditions, original currency/amount and highest priority; equal-priority conflicts stay unresolved and mappings are whitelisted so rules never grant approval or change source identity.
- Import manifests and overlap/outcome counts are pure in import-manifest.ts; each file has reviewed account/currency/period, detected transaction ranges never certify coverage, and post-interruption outcomes read persisted fingerprints rather than trusting response counts.
- Import inbox grouping/search validation lives in import-inbox.ts; batch links open owner-visible staged review only, never posting, and active reviews refresh with stale-response protection.
- Import approval previews and authenticated posting share source amount/date/currency and statement-account direction guards in historical-import.ts, matching the atomic posting checks so invalid movements never appear eligible.
- Statement review grouping lives in import-groups.ts as a pure presentation function; group totals use original amounts with incoming/outgoing kept separate, and grouping never changes classifications or approval.
- Import recurring-pattern hints reuse planning.ts cadence detection via import-patterns.ts, partition by account/currency/type/direction and retain every source row; hints never create commitments or treat repeats as duplicates.
- Classification learning uses import-learning.ts for conservative merchant/account/currency/type/direction matches; reusable mappings omit source identity and approval, and propagation leaves matching unconfirmed rows under review.
- Scanned imports extract four PDF pages per leased run with durable per-page results and owner AI pause guards; source balance quotes stay separate from user balance review, and matching arithmetic never certifies ledger completeness.
- Trip metadata batches use manage_trip_expenses with owner and reviewed-snapshot checks, never monetary writes; smart-trip-suggestions are pure and require explicit linking. Travel inbox derives confirmations from vault attachments and stores manually added messages in owner preferences; it has no external email connection.
- Trip discovery filters are pure in trip-filters.ts: selections combine within a field and intersect across fields, date ranges overlap inclusively, and filtering never changes trips or ledger data.
- financial-review-intelligence.ts adapts saved narration to existing confirmed rule conditions without altering records; category-only ready suggestions require unchanged responsibility, and recurring cohorts partition ownership/type/claim treatment before reusing cadence detection.
- Trip budgets follow trip-budget.ts: one primary budget per trip; workspace/traveller/category/currency/organisation allocations are independent views that reconcile against it and are never summed together; actuals come only from the shared ledger via tripFinance, unpaid bookings stay commitments, and a budget-less trip with saved allocations shows "requires confirmation" rather than an auto-derived total.
- Recipient links: expenses.payee_id references an owner-preferences payee (bulk via apply_review_metadata 'payeeId'); money lent/borrowed with outsiders is an other_asset/other_liability account with details.payeeId, moved by transfers so it never counts as spending or income.
- Trip advances apply to claims only as a user-entered amount per claim (applyAdvance in expense-claim.ts), capped by advance not applied in earlier saved claims; never automatic.
- Reports Centre PDFs are built from src/lib/report-centre.ts (pure, reuses ledger/workspace/travel rules) and rendered by src/lib/report-pdf.ts; generated PDFs are frozen snapshots in report_history + owner receipts prefix so later edits never change them.
- Detailed Expenditure Statements are pure (src/lib/expenditure-statement.ts) and merged with original bills by pdf-lib in src/lib/expenditure-pdf.ts; payer, payment source and eligibility come only from saved entry, instrument and reimbursement records.
- PDF table cells with non-Latin text are rendered by the browser onto canvas images (src/lib/pdf-unicode.ts withUnicode) because jsPDF core fonts are Latin-only and cannot shape Indic scripts; titles, footers and bill-page labels use textU()/drawTextU() which image-render non-Latin text.
- Internal transfers: transfer_links (owner-read RLS, unique active debit/credit) written only by confirm_transfer/cancel_transfer RPCs; the debit becomes the single transfer movement and the credit keeps statement evidence via expenses.transfer_counterpart_of, which ledger/cashflow and store.transactions exclude so it is never counted twice. transfer-match.ts suggests pairs; "strong" needs a shared reference or narration naming the other account, never amount alone, and every link still requires confirmation.
- transfer-audit.ts is a read-only records check from April 2026 against uploaded statement lines pooled per account; coverage uses the dates the lines actually span, and findings never write records.
- trip-lifecycle.ts: cancel/restore only set cancelledAt/restoredAt; delete unlinks entries and is blocked while advances or claims are open. card-balance.ts derives running card owed from accountBalance; payments are reconciled only when reconciledAt is set.
- correction-fields.ts TXN_INTENTS maps the 13 "What is this transaction?" choices onto existing ledger types; loans/advances use receivable or borrowing accounts, reimbursement stays in the claim flow.
