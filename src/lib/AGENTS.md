# Finance rule modules
- Private file URLs re-check current shared-document visibility and storage RLS on issuance and expire after one minute; revoked access blocks new URLs but previously issued bearer URLs survive until expiry.
- Original-document insert errors require owner read-back before file cleanup; an unknown outcome retains bytes and reports recovery rather than deleting possibly committed evidence.
- Phone notification choices live in owner preferences and notification-settings.ts; funding pushes use independent daily device claims so earlier payment reminders cannot suppress them.
- Subdirectories hold the rest of these notes: src/lib/statement-pipeline/AGENTS.md (statement, import and transfer rules), src/lib/books/AGENTS.md (books, tax, GST, asset and compliance rules) and src/components/AGENTS.md (review, claim, trip, report and receipt-reading rules).
- payees.ts stores external directory records in owner preferences; explicit selection fills the existing merchant draft only, never an owned account or automatic financial classification. Directory changes do not relabel old ledger records. Payees are archive-only: proposed P9 B4 keeps every stored payee when a signed-in write (API, app save, older-backup restore) leaves one out, so expenses.payee_id never dangles; erasure removes the whole preferences row.
- correction-fields.ts derives draft account fields from ledger movement/target rules; it never changes financial treatment or substitutes external payees for owned accounts.
- V5.4 financial audit fixtures run only in memory; defect regressions assert real passing outcomes, and unresolved expected failures must never be counted as successful acceptance.
- Position reimbursement totals use outstandingOf on tracked expense claims; legacy workspace reports use workspaceParts, and manual loan splits use stored-INR repaymentParts while preserving principal-only legacy/EMI entries.
- Family permission SQL has an isolated PGlite regression covering active, unrelated and revoked requesters plus owner decisions; cloud tests must never create sample records in production.

- Personal/family tracker, no approvals: expense rules live as pure tested functions in src/lib/expenses.ts.
- Accounts/ledger rules (balances, cashflow, net worth) are pure tested functions in src/lib/ledger.ts; balances are derived from entries, never stored, and transfers/card payments never count as income or spending. store.expenses = expense-type only; store.transactions = all entries.
- Planning math (recurring schedule, forecast, safe-to-spend, loans, goals, subscription detection) lives in src/lib/planning.ts; src/lib/position.ts combines records into screen/AI figures. The AI assistant (src/lib/assistant.functions.ts) only explains facts from position.ts — never let it compute numbers.
- Mutual fund portfolio charts use pure tested rules in src/lib/portfolio.ts on owner-visible NAV snapshots; gain is change since the first saved NAV net of ledger flows, not lifetime return, because acquisition cost is not recorded.
- Long-range predictions are pure tested rules in src/lib/projection.ts (editable category inflation assumptions); suggestions are rule-based from those figures, not AI, so numbers stay verifiable.
- Financial inbox, data freshness and balance-discrepancy checks are pure derived rules in src/lib/inbox.ts; items are never stored, only dismissals, so they clear automatically when records are fixed and discrepancies never auto-create entries.
- Reimbursement claim detail lives in expenses.reimbursement (src/lib/reimbursements.ts); money back is a linked reimbursement-type entry, never income, and reimbursement_status is derived from it.
- Health score (src/lib/health.ts) and monthly review figures (src/lib/monthly-review.ts) are computed by tested rules; the AI only narrates saved reviews, which store a data hash to flag outdated reports.
- Phase 2/3 rules (simulator, behaviour, emergency fund, irregular bills, milestones, trips, merchants, weekly brief) are pure tested functions in src/lib/intelligence.ts; their settings live in finance_preferences, trips link entries by a 'Trip: <name>' tag so stored INR and exchange rates are never rewritten, and simulations never write records unless the user explicitly saves a planned commitment.
- Saved payment methods (UPI IDs, cards, wallets, cash) live in owner-scoped finance_preferences.paymentInstruments with pure tested rules in src/lib/payment-instruments.ts; each is linked to an account of a compatible kind and entries keep the method id plus the general payment type, so balances still flow through the linked account.
- Currency conversion happens server-side in src/lib/fx.functions.ts (Frankfurter/ECB rates for the bill date) so stored INR amounts can't be faked by the client.
- Reports are generated in the browser (src/lib/reports.ts) from data the user can already see, so RLS scoping applies automatically.
- Report history saves require exact owner/id/path/size readback even after an acknowledged insert; unknown outcomes retain evidence and retry the same identity.
- Vault document scanning uses a server function (src/lib/document-extract.functions.ts) gated by the same AI privacy settings; extracted fields are always reviewed before saving.
- Category splits live in expenses.allocations and all category reporting goes through categoryTotals/categoryParts so a split transaction is counted once.
- Mutual fund NAVs are authenticated server-fetched daily quotes; reviewed units create dated valuation snapshots, never income or expense entries, so net worth reuses the ledger engine.
- Universal entry presentation rules (recent-first ordering, which detail groups show, date shortcuts) are pure functions in src/lib/entry-form.ts; they never decide amounts or what is saved, so the one save path stays unchanged.
- correction-fields.ts TXN_INTENTS maps the 13 "What is this transaction?" choices onto existing ledger types; loans/advances use receivable or borrowing accounts, reimbursement stays in the claim flow.
- Recipient links: expenses.payee_id references an owner-preferences payee (bulk via apply_review_metadata 'payeeId'); money lent/borrowed with outsiders is an other_asset/other_liability account with details.payeeId, moved by transfers so it never counts as spending or income.
- Expense drafts live in owner-RLS expense_drafts (src/lib/drafts.ts) with receipts under the owner receipts prefix; drafts never enter the ledger, share their id with the eventual transaction so a repeated Save is idempotent, and are marked saved (files removed) after the real save. Every draft edit is first written to an encrypted owner-bound device copy (offline.ts snapshots store) and synced on start-up/online with newer-copy-wins, so offline edits survive closing the app.
- Device MPIN (src/lib/mpin.ts) is a device-only quick unlock: salted PBKDF2 hash per owner in local storage, erased after five wrong tries; it only opens an existing session, never signs in.
- Smart defaults per field and per-shop rules (shopRules keyed by trimmed lower-case shop name, shopAliases mapping other spellings to that key via resolveShop) are owner preferences applied before suggestions reach New expense; a self-picked account is never replaced.
- Upcoming payments are marked done via mark-done.ts (only an active commitment's current or overdue due date, once each); bulk uses scheduled amounts through confirmCommitment after an in-app confirm.
- Master-record rules (duplicates, organisation usage/rename) live in src/lib/master-data.ts and setup readiness in src/lib/setup-status.ts; every add-account path uses the shared AccountForm so contextual and central creation follow one rule set.
- Receipt-viewer problem reports keep device and browser reading in pure rules (src/lib/device-report.ts) so a saved report can be re-read years later without the phone that made it; the viewer's last twelve moves travel with the report, and reports are never financial records.
- Team access goes only through can_access_expense / team_company_tax (admin role_permissions, app_admins); store filters expenses to own employee_id so team rows never enter personal totals.
- Backup reads explicitly filter each table by its owner field, including employee_id on expenses, because team-visible records must never enter personal exports; recovery browser checks block external writes and use isolated records/storage.
- Original-file downloads go through store.downloadFile → fetchPrivateFile (private-files.ts): fetch the signed bytes, refuse empty/size/checksum mismatch, save via downloadBlob; opening a cross-origin signed URL never saves a file.

- INR ledger, expense allocations, statement balances, repayment history, planning/allocation, portfolio, asset schedules, tax source/liability and report sums use src/lib/money.ts decimal arithmetic with existing rounding boundaries; numeric storage stays unchanged to preserve compatibility.
- KK decision 11 Nov 2026 (docs/workstreams/DECIMAL_PRECISION_2026-11-11.md): reimbursement, claim, statement, organisation-share and travel-report sums also use money.ts (half-up once at paise). Read bills keep source digits as evidence; receiptPrecisionFlags flags amounts finer than the currency minor unit and postingPrecisionError refuses anything finer than stored precision instead of letting numeric(14,2) round it silently.
- Trip complete-allocation dimensions are explicit owner preferences; changes validate each promised dimension independently against the primary budget without auto-combining plans.
- Prepared report saves use stable IDs, owner/size/path readback and same-blob retry; unknown insert outcomes retain uploaded evidence rather than deleting possibly committed files.
- Merchant grouping compares every original name before/after, binds affected records to review and retains reversible alias history in owner preferences; reversal refuses later dependent edits and never rewrites ledger sources.
- Budget utilisation rules use saved category limits and split-aware monthly spending; transfers never contribute and thresholds are finite owner choices.
- Background report retries retrieve an existing PDF before loading new figures, verify readback bytes and store SHA-256 in history filters; completion rechecks saved evidence, so missing/corrupted originals never become successful jobs.
- request-dedupe.ts shares identical in-flight reads (nothing cached after settle) and throttles background session re-checks; screens poll only while work is actually running, so page opens don't repeat the same queries.
- Statement Inbox registration (statement-line-claims.ts, P0-025) claims lines before saving and saves each with a stable per-line entry id (owner + fingerprint), so repeats, retries and re-imports add no second entry; a failed imported-lines read blocks Register (never a partial set). Proposed P9 SQL makes the claim database-backed; until installed the fully read set + stable ids apply.
- store.removeDocument only clears a used "saved to add later" receipt's staging copy after its bytes were saved with an entry (pending-documents.ts; P9 discard_used_pending_document verifies the copy); every other document, loan, goal, payment or valuation is archived, and P9 refuses their deletes by signed-in users.
- Statement line references (statement-fingerprint.ts statementLineSourceRef, RB-STM-01) derive only from the line fingerprint (statement account + date, direction, amount, bank reference or normalised narration, #n); the file name is never part of the source identity, and an entry keeps a reference it already holds.
- Entries are never deleted by the user (entry-removal.ts): posted → reverse; unposted and unreconciled → Withdraw with reason (withdrawal.ts / withdrawal.server.ts; P10 withdraw_entry), kept with receipts and history, excluded by ledgerView, restorable; reconciled entries go through correction.
- While the app is locked (app-lock-state.ts, set by the lock screen) lock-gate.ts pauses background financial work: the store issues no cloud read, offline flush or paint, a load the lock interrupts never paints, and the authorised unlock flushes then refreshes exactly once; page pollers and focus/online refetches skip their ticks.
- Locked evidence (documents.evidence_locked) keeps its file too: store.removeDocument refuses it first (evidence-lock.ts) and proposed P17 adds RESTRICTIVE storage.objects delete/update/insert refusals that trust only the documents row (no session-setting exemption). R14: store.areaStatus/useAreaStatus give loading/offline/unavailable/denied/failed/empty/ready per area (unavailable = offline and never read on this device: no figures, no empty state; offline = device copy or earlier read, from store loadedAreas); a denied area is cleared from memory and not painted from the device copy until a read succeeds.
- R14b read truth (store.tsx / load-state.ts): `syncState === "error"` means "some area failed, or the whole read failed"; never use it as a whole-read signal. `readFailure` (set only in loadRun's catch, cleared by the next read that completes) is the whole-read failure signal. `confirmedAreas` lists areas a cloud read confirmed this session; the encrypted device copy is still painted first but never confirms, so online an unconfirmed area reads 'loading' (or 'failed' once readFailure is set) with `cached: true`, and only a confirmed area reads 'empty'/'ready'. Absence ("no records", "not found", "no access", ₹0) is claimed only from 'empty' (areaConfirmedEmpty); provisional values may paint when areaMayPaintValues. Offline and denied behaviour are unchanged, and the device copy is not rewritten after a whole-read failure. Reconnect truth: on the 'online' event or the store's `online` going false→true, the store flushes queued offline entries and then runs exactly one refresh when syncState is 'offline', readFailure is set, or a settled area is not cloud-confirmed (or entries were saved); concurrent triggers share one run, an in-flight read is joined, and syncState reads 'syncing' while it runs. Online, a readFailure of any kind is a whole-read failure (unconfirmed areas read 'failed' with `cached`; Ctx.readFailure reports kind 'failed' once online) until a read completes. Offline signal: screens decide "offline" only from the store's `online` (offline = `!online`) or areaStatus 'offline'/'unavailable', never from `syncState`. Owner ruling (offline absence wording, DocuRepo pattern): offline, an absence shown from the device copy must say so — use `offlineAbsence(what)` from load-state.ts ("No assets in the copy saved on this device") — and must never read as plain fact.
- Claim receipt correction (receipt-correction.ts; proposed P20 finance_operation 'correct_claim_receipt', after P19): `store.correctReimbursementReceipt(e, { receiptId, newAmount, reason, operationId })` only REDUCES one receipt citation (0 removes it; txnId/date/account never change; increases stay with addReimbursementReceipt), needs a reason, refuses offline ("Reconnect to update this claim"), is idempotent by operationId (keep one id per user confirmation; retries reuse it), recomputes reimbursement_status as statusColumn does and writes an owner-read-only claim_receipt_corrections audit row (before/after, reason, actor). Use it for an "already counted on another claim" citation (reduce to the uncounted part); updateReimbursement still keeps saved receipts. Until P20 is installed the server answers "Unknown operation". The offline refusal reads the store's `online` (submitReceiptCorrection takes it; store `operation` uses onlineRef), never navigator.onLine. P20 rollback retains claim_receipt_corrections read-only (owner RLS reads; grants, RLS and phase3_p20_retained triggers refuse every write except the erasure cascade) and re-install keeps those rows and appends.
