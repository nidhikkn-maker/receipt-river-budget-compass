**Status:** proposed SQL, tested **in isolated PGlite only**. Not applied to Lovable Cloud, Live or any hosted database. Nothing deployed, merged, pushed or committed. No production data has been migrated.

## 1. KK's permanent-ID decision (decided 9 Nov 2026, binding)

| # | Decision | How P5 implements it |
|---|---|---|
| 1 | Every record has a globally unique, immutable internal ID (uuid primary key), never changed, reused or regenerated by migration | Every new table uses `id uuid PRIMARY KEY`. No P5 statement updates an existing `id`. Backfill and restore never generate replacement ids. `register_records.id` is the permanent ID that the registers will reuse as their own primary key. |
| 2 | Readable numbers are assigned **within the company or personal accounting scope**: counters keyed by legal entity (a company's `legal_entities` row, or the owner's `individual_personal` row), not per account owner and not global. Uniqueness is (scope entity, prefix[, year], number) | `readable_id_counters (scope_entity_id, prefix, year)` and `readable_id_registry PRIMARY KEY (scope_entity_id, readable_id)`. `issue_readable_id` runs in the same transaction as the insert (the BEFORE INSERT trigger `assign_readable_id`), so a rolled-back insert spends no number. Numbers only move forward and are never reused. `claim_readable_id` keeps an existing number on restore or import, refuses a number already held by another record in that scope, and moves the counter past it. Two companies each get their own `AST-000001` / `PRP-0001` (tested). |
| 2a | Records without an entity scope get no readable number until linked | The generic trigger issues nothing while the scope column is NULL. A number given without a scope is refused (`READABLE_ID_NEEDS_SCOPE`). Once linked, the number is issued in that scope and **kept** if the scope later changes (tested on a probe table). **How they show:** the legacy id (for example `LL-DES-20260410-3fa9c1`, a JSON id or an asset `tag`) or the first 8 characters of the uuid, labelled "unlinked". |
| 3 | Jointly owned properties keep **one** permanent property ID across all owners; ownership shares and effective dates are held separately (no overlapping ranges per (asset, owning entity); total ≤ 100% on any date) | `register_records` is the single anchor (uuid plus one PRP/AST number). `record_ownerships` holds one row per owning legal entity of **any** account: share %, `valid_from`/`valid_to`, evidence document, status. Trigger rules (every role): no overlap per (record, owning entity); confirmed shares ≤ 100% on every date; rows are ended or rejected, never deleted. |
| 4 | Historical records and IDs stay unchanged during migration. No existing uuid, legacy id, `LL-DES-`/`LL-CLM-` reference or JSON id is altered. Readable numbers sit beside them | P5 adds **one nullable column** (`legal_entity_id`) to three tables. It changes no other value: every pre-existing row is hashed before and after apply, preview, commit, re-commit and the owner-confirmed orphan commit (identical). JSON is only read. `entity_key` keeps the JSON `entities[].id` as a permanent alias. |

Formats (from "Permanent IDs (revision 8)"; the digit count is a **minimum**, so numbers never wrap): `ENT-NNNNNN` (new, legal entities, numbered in the owner's personal scope), `AST-NNNNNN`, `PRP-NNNN`, `TRP-YYYY-NNNN`, `EXP-YYYY-NNNNNN`, `CLM-YYYY-NNNN`, `DES-YYYY-NNNN` (versions keep the number and add v2, v3), `EVT-/REM-/NTF-YYYY-NNNNNN`.

**Applied in P5:** ENT (legal entities) and PRP/AST (register records). The other formats are registered. Their tables attach the same trigger when they are built (registers step) or, for expenses, at the write switch. Existing expenses are **not** numbered by P5 (see §9, deviation D1).

### 2.2 Additive columns (nullable, trigger-maintained, never written by clients)

`expenses.legal_entity_id`, `documents.legal_entity_id` and `opening_postings.legal_entity_id`, each with an owner-composite FK to `legal_entities(owner_id, id)`.

`opening_postings` is included because its `entity_id` is a NOT NULL company key used by P3 opening balances, so it must resolve to the same legal entity.

Trigger `zy_p5_link_legal_entity` (BEFORE INSERT OR UPDATE; named so that it runs after every applied BEFORE trigger and before P1's `zz_` guards) resolves the link:

- Expenses follow the app's `effectiveEntity` rule: a hand-picked company (`entity_source='manual'`) wins; otherwise the paying account's company on the entry date, from the dated assignment or, when none exists yet, the legacy JSON.
- Documents and opening postings use their `entity_id`; a NULL document `entity_id` means the owner's personal books.
- An unknown key or an account listed under two companies resolves to **NULL**, which is reported and never refused. A client-supplied value is always recomputed.
- An UPDATE whose only effect is the link keeps `expenses.correction_revision`, because applied trigger 0041 bumps it on every update. `log_transaction_change` does not track the column, so linking writes no audit row (tested).
- Before the owner's backfill (no personal entity yet), everything stays NULL.

### 2.3 Overlap rule: trigger, not exclusion constraint

`EXCLUDE USING gist (account_id WITH =, daterange(...) WITH &&)` needs the `btree_gist` extension. It is not loaded in the isolated PGlite harness, so the constraint could not be tested. Installing an extension on hosted needs separate approval, and a rollback would either leave it behind or risk dropping a pre-existing copy.

P5 therefore uses BEFORE INSERT/UPDATE triggers (`guard_account_entity_assignment`, `guard_record_ownership`):

- They take a per-account (or per-record) `pg_advisory_xact_lock`, then check ranges as `daterange(..., '[)')`.
- They apply to every role, including definer code and the table owner (tested as superuser).
- Under READ COMMITTED (the Supabase default) the query after the lock sees every committed row.

Concurrency across real connections is pre-check H-P5-6. If `btree_gist` is approved later, an exclusion constraint can be added beside the trigger.

## 4. Backfill rules (what is and is not mapped)

- **Mapped:** JSON `entities[]` with a valid kind → one legal entity each. The key is kept verbatim, including intake-run-id keys, which are reported as `intake_run_entity_key` info and kept as the permanent alias. Each owner gets a personal entity. Each account in `books.entityAccounts` → a frozen assignment.
- **Never mapped:** Me/Family/Business/Official workspace labels (`expenses.scope`), `Organisation: <name>` tags, reimbursement profiles, trip organisation names, payees, family members, the `self` sentinel. The test asserts that these labels do not appear anywhere in the preview, and that a `business`-scope entry tagged `Organisation:` stays personal.
- **Orphans (deleted or merged companies):** keys used by rows (expenses, documents, opening postings, entity members, closed periods, asset/property/holding owners, FY records) that are missing from `entities[]` are reported as `orphan_entity_reference` errors and left **unresolved (NULL)**. They are never guessed and never remapped to the merge target (DN-P3-9). Only with the owner's explicit `_archive_orphans = true` does each one become an archived `legacy_unknown` entity, so history links to it, and the report reaches `match`.
- **Ambiguities:** an account listed under several companies → `account_linked_twice` (never linked, entries NULL; a reassign is refused with `REASSIGN_NEEDS_BACKFILL` until resolved). Other cases are only reported, never merged automatically: same PAN (a proprietorship shares its proprietor's PAN, so there is no unique PAN constraint), same normalised name, conflicting duplicate keys, reserved `personal:` keys, invalid or unknown account ids, an entity changed since the backfill, an assignment that differs from the JSON.

## 5. Generic backfill framework (for the registers developer)

The registers step (assets, properties, trips, holdings, leases, receivables, journals) reuses the following:

1. **Enumerate** a JSON list with provenance: `legacy_json_elements(data, ARRAY['books','properties'], 'id')` gives `(ord, path 'books.properties[3]', legacy_id, element, element_sha256)`. Non-arrays yield nothing; report them with `legacy_exception('not_a_list','error',path,NULL,…)`.
2. **Exceptions:** `legacy_exception(code, severity error|warning|info, path, legacy_id, detail)`. An error blocks only that item's link and never the whole run.
3. **Source hash:** `legacy_sha256(jsonb_build_object(<the sections read>))`. Commit recomputes it under the owner lock and refuses on change.
4. **Idempotence:** a unique key on `(owner_id, kind, legacy_id)` (as in `register_records`). Commit inserts only plan actions `create`. Never use `INSERT … ON CONFLICT DO NOTHING` on a table with a readable-number trigger: the BEFORE trigger fires before conflict detection and would spend a number (this defect was fixed in this file).
5. **Provenance:** store `source = {from, path, legacy_id, element_sha256, source_sha256, source_revision, run_id, captured_at}` on every created row, and append a `legacy_backfill_runs` row with kind `<register>`.
6. **Compare:** build `{key: aggregate}` maps before (legacy) and after (tables) and call `legacy_compare_maps(before, after)` → `{identical, before_keys, after_keys, differences[]}`.
7. **Readable numbers:** add `readable_id text` plus `legal_entity_id` to the register and `CREATE TRIGGER a_assign_readable_id BEFORE INSERT OR UPDATE … EXECUTE FUNCTION assign_readable_id('<PREFIX>', '<date column>', 'legal_entity_id', 'owner_id')`. A legacy number brought along is claimed, not reissued. Rows without an entity stay unnumbered until linked.
8. **How registers attach to shared records:** `properties.id uuid PRIMARY KEY REFERENCES register_records(id)` (same for `assets`), with `register_records.record_kind` matching. The register row then **is** the shared record: one id and one PRP/AST number for every co-owner. The administrator's per-owner details live in the register row. Each co-owner's share lives in `record_ownerships`. Register RLS should reuse `p5_can_read_register_record(id)`. Legacy JSON `assets[]`/`books.properties[]` are imported with `register_shared_record(kind, entity, label, legacy_id)` semantics (idempotent per legacy id). A legal transfer keeps the record and number; it ends one share and starts another.

## 6. Data-preservation evidence (isolated)

- Every pre-existing table (all `public` tables at P1+P2+P4 except the P4 step-up/audit tables written by the tests themselves, plus `storage.objects` and `auth.users`) is hashed per row with count and md5 of `to_jsonb(row) - 'legal_entity_id'`. The hash is identical after: P5 apply, preview, a refused stale commit, commit, re-commit, and the owner-confirmed orphan commit. It covers `correction_revision`, the `entity_id` text, the preference JSON and revision, storage paths, and `transaction_audit` (no new audit rows).
- Balances per entity/account/currency/month/type, as computed by the app's own `effectiveEntity` (TypeScript, imported from `src/lib/books/entity-accounts.ts`), equal the balances grouped by the stored link, and the SQL report says `match`.
- After rollback: the catalog (policies, function definitions and ACLs, triggers, indexes, constraints, tables, columns, table and column grants, RLS flags, schemas) equals P1+P2+P4 exactly. Data hashes are identical. All P5 rows are kept in `security_rollback_archive`.

## 7. Rollback steps

1. **KK approval.** Export the P5 tables if needed.
2. Run `P5_legal_entities_foundation.rollback.sql` (one transaction). It:
   - drops the P4 wrappers and `__unguarded` copies of the P5 entry points and removes their registry rows (their `security_events` rows are kept);
   - drops the link and erasure triggers;
   - restores `guard_closed_period`, `guard_journals_rules` and `ll_closed_on` from the saved definitions (same oid and grants);
   - copies every non-NULL `legal_entity_id` to `security_rollback_archive.p5_ledger_links_<UTC>`, then drops the three columns (their FKs go with them);
   - removes policies, triggers and FKs to live tables from the nine P5 tables and **moves** them to `security_rollback_archive.p5_<table>_<UTC>`, with no client or service_role access;
   - drops the P5 functions and the `phase2_p5` schema.
3. Then, if wanted, run the P4 rollback, which now refuses while P5 is installed.
4. **Re-applying after a rollback** starts empty counters. The numbers in the archive would be issued again to new rows, under new scope uuids. Before re-applying in production, restore `readable_id_counters` and `readable_id_registry` from the archive (residual risk R6).

## 9. Deviations from the inventory sketch (and why)

- **D1. No EXP numbers on existing expenses in P5.** Numbering about 100k legacy rows means choosing an order (date? id?) that becomes permanent, and the inventory's stage 1 says "no triggers that change existing writes" for financial rows. Formats and the generic trigger are ready. Numbering starts at the write switch for new expenses, with legacy rows numbered by a separately approved, previewed run.
- **D2. No `UNIQUE(owner_id, pan)`.** A proprietorship shares its proprietor's PAN. Same-PAN entities are reported (`possible_duplicate_pan`) and never merged.
- **D3. Trigger instead of an exclusion constraint** (§2.3).
- **D4. `register_records` added** (not in the sketch). Without an anchor, any signed-in user could insert a 100% share against an arbitrary uuid and block the real owners. The anchor also gives the property its one permanent number and a consent model for co-owners.
- **D5. Account deletion cascades its assignment history.** `ON DELETE RESTRICT` would refuse a delete that is valid today. The app UI archives accounts rather than deleting them; only demo cleanup and erasure delete.
- **D6. Erasure is refused** (`ERASURE_BLOCKED_COOWNED`) while another account holds shares of a record the erasing owner administers. This keeps shared evidence; KK decision C13 (erasure scope) is still pending.

## 11. Residual risks

- **R1. PGlite is not Supabase.** Policies, definer ownership (`rolbypassrls`), advisory locks across connections and PostgREST behaviour need the hosted pre-checks.
- **R2. Dual-read drift.** Until the write switch, the app moves accounts only in JSON and `reassign_account_entity` only in the table. The closed check is conservative (union), but the link column follows the table. The report shows the drift.
- **R3. jsonb key order.** For an account listed twice, the legacy "before" side cannot reproduce the app's insertion-order choice. Such rows are never linked and always show as differences.
- **R4. Restore and readable numbers.** `restore_finance_backup` does not carry P5 tables yet; backup v3 (the parallel backup work) must include them and claim numbers with `claim_readable_id`. A cross-account restore resolves links in the restoring owner's scope; it never copies the source owner's entity.
- **R5. Workspace-wide P2 grants** (`entity_id` NULL) see every company row of that owner, never personal books. That follows from P2's grant semantics.
- **R6. Rollback archives the counters.** Re-applying without restoring them would reissue human-visible numbers (under new scope uuids).
- **R7. Erasure versus shared records** (D6) waits on KK decision C13.
- **R8. P3 interaction.** P3's `ll_closed_on` calls become stricter only for periods with an empty `entityId`. P3 was not re-run on top of P5 in this phase; P3's `entity_exists` should switch to `legal_entities` in its revision.
- **R9. Same-account restore of rows inside closed periods** is refused today (0058's BEFORE INSERT fires before ON CONFLICT). This is pre-existing, unchanged by P5, and noted for the backup developer.
- **R10. Monthly depreciation cron and intake commit** still write only JSON (inventory R13). Their records get links and numbers only at the write switch.

## 12. P5b: investments inside the one restore transaction (`P5b_restore_investments.sql`)

**Problem.** Applied `restore_finance_backup` (0072) restores 11 tables. Backup format 3 also carries `demat_accounts` and `security_holdings`. Today the app writes those two tables in a second client step after the RPC (`investmentTablesToWrite` in `src/lib/backup.ts`, used by `settings.tsx`), so a failure there leaves a half-restored account.

**How each layer wraps the function:**

- P1 and P2 do not touch it.
- P4 guards it **inline**: the original is renamed `restore_finance_backup__unguarded` (clients lose EXECUTE), and the public name is re-created from the 0072 text with `PERFORM public.require_recent_step_up('restore_finance_backup');` as its first statement. It stays SECURITY INVOKER.
- P3 (not in this chain) renames the public function to `accounting_private.restore_finance_backup_0072` and wraps it. If P3 is revised to sit on top of P5b, it must wrap the P5b body instead of the 0072 one (residual risk R11).

**Change.** `CREATE OR REPLACE` of the P4 public function (same oid, owner, grants, signature, return type, SECURITY INVOKER and search_path), pinned by the md5 of the P4 form.

- The original definition is saved in `phase2_p5b.saved_functions`.
- The body is the 0072 body unchanged, with the step-up check first, plus a block after `documents` that handles `demat_accounts`, then `security_holdings`:
  - Owner forced to `auth.uid()`; RLS applies (the holdings policy requires the owner's own demat account).
  - Matching by natural key: `(owner, dp_id, client_id)` for demat accounts and `(owner, demat_id, isin)` for holdings.
  - Same natural key under a **different** id: the existing row is kept unchanged and the incoming id is mapped to it (holdings follow their demat account). Differing values are returned in `investmentConflicts` (`{table, backupId, keptId, differences{field:{kept, backup}}}`), and the mapping in `investmentIdMap`.
  - Same id: the ordinary restore upsert, exactly like every other table.
- `counts` now always contains both tables (0 for v1/v2 backups), so `investmentTablesToWrite` returns `[]` and the app's second step never runs. **No app change is needed.**

**Rollback.** `P5b_restore_investments.rollback.sql` re-executes the saved P4 definition and drops `phase2_p5b`. Restored rows stay. The P4 rollback refuses while P5b is installed.

## 13. opening_postings ids (assessment and fix)

- `opening_postings.id` is a **global** primary key (`PRIMARY KEY (id)`, from 0061). `OpeningBalances.tsx` derived it as `stableId("opening-post|<entity key>|<fy>|<count>")`.
- Entity keys are the same text under different owners: they are copied with preferences on a cross-account restore, and independent owners can share them. A second owner's first post for the same company key and year therefore produces the same uuid. `post_opening_balances` finds no row of its own and fails on the primary key, which blocks that owner. This is reproduced in the test.
- Line entry ids include the account uuid, so they do not collide.
- **Fix (app only, no SQL, no existing id changed):**
  - `openingPostingId(owner, entityId, fy, n)` in `src/lib/books/fy.ts` puts the owner in the derivation.
  - `OpeningBalances.tsx` uses it with the store's `userId`.
  - Runs already stored keep their ids. Retries stay idempotent, because the same inputs give the same id.
  - Per-owner uniqueness of active runs is already enforced by `opening_postings_active (owner_id, entity_id, fy) WHERE undone_at IS NULL`.
- A database-side alternative (an owner-composite key) would change the primary key of an applied table and is not proposed.

### 15.1 Objects per register

The common contract applies to every table:

- **ID:** a uuid primary key, permanent and never regenerated.
- **Owner:** `owner_id`.
- **Scope:** a legal entity. For assets and properties the scope is the `register_records` scope.
- **Readable number:** issued per KK's rule.
- **Provenance:**
  - `legacy_id`;
  - `legacy_element`, the raw JSON element, read-only, so no field is ever lost;

### 15.2 Rules

- **References instead of totals (FND-03).** Money lives in ledger entries; registers point to them by id.
  - The ids are checked on insert by `p6_guard_references` (the owner's own rows only).
  - There is **no FK** to expenses, accounts, documents, loans or security holdings, so a delete that is valid today is never refused.
  - A later delete shows up as an orphan in the compare report.
- **Identity is fixed for every role, the table owner included** (`p6_guard_register_row`):
  - The only changes allowed are archiving once (`archived_at/by/reason` from NULL) and ending a containment once (`valid_to`).
  - Deletes happen only by confirmed erasure (`ledgerline.erasing`).
- **Never guessed:**
  - an unknown `ownerEntityId` (a deleted or merged company);
  - a trip name shared by two trips (no tag links for either);
  - an advance's or receivable's ledger entry;
  - a holding whose ISIN matches several demat rows.

  Each of these is an exception. An error blocks that item only.
- **Labels never become entities** (FND-02, R1). Trips, receivables and projects default to the owner's personal scope, and an info exception is raised where the JSON carries an organisation or workspace label.
- **Joint property (DN-P2-IDS item 3).**
  - One `register_records` row and one PRP number.
  - The administrator's `properties` row is the shared register row.
  - Co-owners hold dated shares in `record_ownerships` (P5 consent: requested by the entity's own account, confirmed by the administrator, at most 100% per date).
  - A co-owner's legacy JSON copy attaches through `_options.attach = {<legacy id>: <record uuid>}` into `register_legacy_copies`.
- **No double counting (Flow 5).**
  - In `register_valuation_report`, every valued property counts its latest valuation once.
  - An asset inside a valued property with `included_in_property_value` is excluded and listed with `counted_within`.
  - Ending the containment counts the asset on its own from that date.
- **Readable numbers.** They are scope-local, issued in the commit transaction, never reused (archived numbers stay taken) and stable across re-commits. A new JSON item later gets the next number.

## 18. Rollback

1. **KK approval.** Export the P6 tables if needed.
2. Run `P6_registers.rollback.sql` (one transaction). It:
   - unguards and drops the 7 entry points (their registry rows are removed; their `security_events` are kept);
   - drops the two triggers on existing tables;
   - **moves** the 17 tables to `security_rollback_archive.p6_<table>_<UTC ms>`. Before the move it removes their policies, triggers, links to live tables and grants, and gives their indexes unique names so a later rollback cannot collide;
   - drops the P6 functions and the `phase2_p6` schema.
3. It **keeps on purpose** (P5 tables):
   - the `register_records` and `record_ownerships` anchors created by the backfill;
   - the `LSE/HLD/RCV/PRJ` formats, counters and registry rows;
   - the P6 `legacy_backfill_runs` rows.

   As a result, a re-applied P6 re-attaches assets and properties to the **same uuids and AST/PRP numbers** (tested). Registers without an anchor (trips and the others) get **new** uuids and numbers on re-apply. A number is never reissued (tested); restoring them from the archive is a separate step (R-P6-5).
4. Then, if wanted, run the P5 rollback, which now succeeds (tested).

## 21. Not delivered, deviations and residual risks

**Not delivered (next slices):**

- `books.propertyCosts`, GST invoices, filings and advances, tax workpapers, `fyRecords`, `loanBalances` and `docLinks`.
- Itinerary items as a table: they are kept as `trips.itinerary` jsonb.
- The co-owner `attach` option for **assets**: the table supports it, but only the properties plan offers it.
- "Project:" tags that have no project budget.
- Writers for descriptive edits, explicit advance and receivable entry links, and sale, disposal and transfer workflows. These are out of scope by decision.

**Deviations:**

- **D-P6-1.** New formats `LSE`, `HLD`, `RCV` and `PRJ` are not in the revision 8 list. They need KK confirmation.
- **D-P6-2.** Archive state and scope for assets and properties live once, on `register_records`.
- **D-P6-3.** Child rows carry no readable number.
- **D-P6-4.** Legacy trips are numbered by the year of their start date, because the JSON has no creation date. Trips without a valid start use the year of the backfill.
- **D-P6-5.** Trips, receivables and projects default to personal books (info exception) because the JSON names no entity.
- **D-P6-6.** References are checked on insert, without FKs, so today's valid deletes are never refused; orphans are reported instead.
- **D-P6-7.** The full raw JSON element is stored (`legacy_element`).
- **D-P6-8.** The valuation report uses the administrator's scope at 100%, ignoring shares. Assets without a valuation event use the legacy cost, marked `legacy_cost_compare_only`.
- **D-P6-9.** The rollback keeps P5 anchors and numbers (§18).
- **D-P6-10.** Tag links reproduce the app's `tripSummary` rule (trip_id OR exact tag), except for ambiguous names.

**Residual risks:**

- **R-P6-1.** PGlite is not Supabase. Definer ownership, advisory locks across connections and performance on large owners (H-P6-4) need checking.
- **R-P6-2. Dual-read drift.**
  - JSON edits made after a commit to an *existing* item are seen only in the money compare (legacy amounts). A purely descriptive edit is not flagged; `source.element_sha256` is stored for a later "changed since backfill" check.
  - New items and links show as pending.
- **R-P6-3.** The monthly depreciation cron, intake and trip SQL still write JSON only (inventory R13). Their records reach the tables only through a new reviewed commit until the write switch.
- **R-P6-4.** Backup and restore do not carry P6 tables (format 4, §22). A cross-account restore of preferences would need a fresh reviewed backfill under the restoring owner.
- **R-P6-5.** Rollback → re-apply gives registers without an anchor new uuids and numbers. Restoring them from the archive needs a separate script.
- **R-P6-6.** Erasure of a co-owned record waits on KK decision C13 (P5 D6).
- **R-P6-7.** P5's own rollback still uses second-resolution archive names and unsuffixed index names. A P5 rollback → re-apply → rollback in the same database would collide (P6 avoids this for its own tables).
- **R-P6-8.** Assistants can read registers (read-only, by P4 design), including legacy money copies.
